== Preface

BirthdayCalendarService (BCS): A Java Spring Boot application that creates and synchronizes a birthday calendar from CardDAV address book data. BCS automatically generates recurring birthday events and maintains them through scheduled synchronization with CalDAV servers like SOGo, Baikal and Radicale. Supports deployment via `command line`, `systemd`, `init.d`, or `Docker containers`.

Features:

* CardDAV/CalDAV integration
* Intelligent event synchronization
* Automated scheduling with cron
* Docker support
* Java 17+ compatible
* Spring Boot 4.x
* Successfully tested with SOGo, Baikal, Radicale +
see below "Backend Tests"

If you find a bug or certain features are missing, don't hesitate to file an issue on https://github.com/th-schwarz/birthday-calendar-service/issues[Github].

== Basic Workflow

The Birthday Calendar Service (BCS) is an application designed to generate a birthday calendar from the contact information stored in a CardDAV address book and upload it to a CalDAV calendar. The working process is built upon key parts and is automated using scheduling methods.

=== General Steps

. Address Book Access
* The application fetches all contacts from one or more configured address books (see `dav.card-paths`) and processes each contact to extract relevant information, such as names and birthdays.

. Event Processing
* The collected birthday data is processed to create calendar events. Each contact's birthday is transformed into a recurring event that adheres to the iCalendar format.
* A calendar "category" is defined to tag birthdays uniquely, allowing the application to manage these events effectively.

. Remote Calendar Management
* The application interacts with the configured CalDAV server and synchronizes the events in the specified birthday calendar. It matches and updates calendar entries to reflect any changes, ensuring that no duplicates or outdated events remain.

. Automation and Scheduling
* The entire workflow is automated using a scheduled method, which is triggered periodically based on a cron expression defined in the application configuration. This ensures the calendar stays up-to-date without manual intervention.

== Setup & Configuration

=== File Structure

Here is the suggested file structure:

[source,bash]
----
├── /opt/bcs
│   ├── bcs.yml    (individual configuration)
│   ├── bcs.jar
│   ├── logback.xml    (logback configuration, optional)
----
*bcs.yml* defines the individual properties. The file is read by default and will be merged with the default properties in the classpath; therefore, the file can be kept as small as possible. A minimal configuration example can be found further below. If the file is inside the working directory, it is loaded automatically.  +
*logback.xml* is an optional Logback configuration file. If omitted, the bundled configuration with a console appender is used. A custom file is *not* picked up automatically: point to it with `--logging.config=/opt/bcs/logback.xml` or the environment variable `LOGGING_CONFIG`.  +
The complete configuration settings can be found link:docs/bcs-configuration.adoc[here].

=== Configuration

Use the individual properties file `bcs.yml` to set e.g., the mandatory dav settings and to override default settings.

The most important settings are:
[source,yaml]
----
bcs:
  calendar-category: Birthday  # default
  cron: "0 30 4 * * *"  # default
  run-on-start: false  # default
dav:
  user: dev
  password: strong
  base-url: https://dav.my-domain.org
  cal-path: /SOGo/dav/dav-user/Calendar/46-12345678-5-87654321/
  card-paths:
    - /SOGo/dav/dav-user/Contacts/personal/
----

- `bcs.calendar-category`: The value depends on the categories of the caldav server and its localization. +
*This value is used to delete and create birthday events, the value must be set correctly initially and must not be changed!*
- `bcs.cron`: The cron trigger used to schedule the synchronization of birthdays.
- `bcs.run-on-start`: Optional parameter, default is false. If it is true, the sync starts immediately on start.
- `dav.user`, `dav.password`: Authentication credentials for the DAV server.
- `dav.base-url`: The base URL of the DAV server (`schema://host(:port)`). All paths below are relative to this server.
- `dav.card-paths`: List of address book paths from which birthdays are read.
- `dav.cal-path`: The path of the birthday calendar which must be created. _To be on the safe side, it's a good idea to use an extra birthday calendar! But it is not mandatory since https://github.com/th-schwarz/birthday-calendar-service/issues/2[A remote event should only be deleted if its categories contain the defined birthday category.]_ was implemented.
- `dav.retry-delay-in-seconds`: This property determines the delay interval (in seconds) between retries in the case of network problems. The default setting is _10_.
- `dav.max-retries`: The maximum number of retries due to network errors. The default setting is _5_.

There are additional settings for the birthday event. For further information have a look at the link:docs/bcs-configuration.adoc[Complete BCS Configuration].

== Start

The fully executable jar can be executed in different ways.

=== by Docker

BCS can be run directly from a container image hosted on GitHub Container Registry (GHCR).

[source,bash]
----
# Run with configuration file mounted from the host
docker run --rm \
  -v /path/to/bcs.yml:/app/bcs.yml:ro \
  -v /path/to/logback.xml:/app/logback.xml:ro  \
  -e LOGGING_CONFIG=/app/logback.xml \
  ghcr.io/th-schwarz/birthday-calendar-service:[tagged-version]
----

Replace `/path/to/bcs.yml` with the absolute path to your configuration file on the host system.
The `-v /path/to/logback.xml` volume mount and the `LOGGING_CONFIG` variable are optional (and only work together); omit both to use a simple console logger.

Allowed values for `tagged-version`:

- `latest` is built from the `main` branch.
- `develop` is built from the `develop` branch.
- a release tag, e.g. `v0.2.0`, is built from the git tag of the same name.
- `feature-xyz` is built from the `feature/xyz` branch (`/` is replaced by `-`).

If you want the application to run once and exit, append the full command including `--run-once`
(the image defines `java -jar bcs.jar` as default command, so a bare `--run-once` would replace it and fail):
[source,bash]
----
docker run --rm \
  -v /path/to/bcs.yml:/app/bcs.yml:ro \
  -v /path/to/logback.xml:/app/logback.xml:ro \
  -e LOGGING_CONFIG=/app/logback.xml \
  ghcr.io/th-schwarz/birthday-calendar-service:latest java -jar bcs.jar --run-once
----

=== by Docker Compose

You can also run BCS with Docker Compose for easier service management.

[source,yaml]
----
services:
  bcs:
    image: ghcr.io/th-schwarz/birthday-calendar-service:latest   # replace with ghcr.io/th-schwarz/birthday-calendar-service:<tag-name> if needed
    container_name: bcs
    restart: unless-stopped
    volumes:
      - ./bcs.yml:/app/bcs.yml:ro          # required configuration
      - ./logback.xml:/app/logback.xml:ro  # optional logging config
    # command: ["java", "-jar", "bcs.jar", "--run-once"]  # uncomment to run once and exit
    environment:
      - LOGGING_CONFIG=/app/logback.xml    # only required when using logback.xml
    #   JAVA_TOOL_OPTIONS: -Xms128m -Xmx512m
    # user: "1000:1000"                    # drop root if desired
----

Start the service:
[source,bash]
----
docker compose up -d
----

Run the container once and exit:
[source,bash]
----
docker compose run --rm bcs java -jar bcs.jar --run-once
----

=== by Command Line

Download the https://github.com/th-schwarz/birthday-calendar-service/releases[last release jar].

The start by command line looks like:

[source,bash]
----
cd /opt/bcs/
java -jar bcs.jar --run-once
----

If you want the application to execute the birthday calendar synchronization only once and then exit immediately, you can use the `--run-once` parameter (one-time processing).

== Known Alternatives

There are other tools for getting contact birthdays into a calendar. Compared to them, BCS:

* writes directly to a CalDAV calendar and keeps it in sync automatically (cron or `--run-once`),
* updates changed events and removes outdated ones without creating duplicates, and only touches events carrying its own category,
* reads from one or more CardDAV address books,
* is tested in CI against SOGo, Baikal and Radicale,
* runs as Docker container, systemd service, init.d service or plain jar.

=== Automated tools

* https://github.com/Adi146/ContactsBDayCalendar[ContactsBDayCalendar] -
Python script (also as Docker image) that adds birthday events from a CardDAV address book to a CalDAV calendar.
_BCS adds built-in scheduling, event matching and updating, and category-based cleanup of outdated events._
* https://github.com/iBigQ/radicale-birthday-calendar[radicale-birthday-calendar] -
server-side script for Radicale; runs as storage hook and updates the birthday calendar whenever a contact changes.
_BCS runs independently of the server, so it needs no server-side hook, and it also works with SOGo and Baikal._
* https://github.com/s-martin/birthday-ics[birthday-ics] -
Docker service that generates a `birthdays.ics` from Nextcloud contacts via CardDAV once a day and serves it via a built-in web server.
_BCS writes real events into a CalDAV calendar instead of providing a read-only ICS feed, and is not tied to Nextcloud._

=== Manual converters (export, convert, import by hand)

* https://github.com/escalate/google-contacts-birthday-ical-calendar[google-contacts-birthday-ical-calendar] -
command line tool (also as Docker image) that converts a Google Contacts CSV export into an iCal file.
_BCS needs no manual export and import and reads the contacts directly from the CardDAV server._
* https://github.com/FoxP/VCF-to-ICS[VCF-to-ICS] -
Python command line script that converts birthdays from VCF files to an ICS file.
_BCS needs no manual export and import, and it synchronizes changes instead of producing a new file each time._
* https://github.com/Weathermann/vcf2ics[vcf2ics] -
simplified Python variant of VCF-to-ICS (reads the BDAY tag and writes the age into the event).
_Same as above._
